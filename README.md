# AI 图像工坊

面向 Windows 的 Photoshop AI 选区编辑、扩图与生成原型。旧版 Photoshop 2018–2023 使用 CEP，Photoshop 2024 起使用 UXP；两端共用本地 Node.js 服务和阿里云百炼适配器。编辑模型为 `wanx2.1-imageedit`，文生图模型为 `wan2.7-image`。

## 已实现

- 选区编辑：空描述自然补全，有描述时按指令局部重绘；整图重绘放在高级设置。
- 扩图：四向比例，或先手工扩大画布并框选规则透明边缘后自动识别；输出尺寸准确时扩展当前 PSD 并以新图层显示新增边缘。
- 文生图：输入描述，默认一张；最多四张候选，预览后才应用。
- 结果预览：点候选图（或图右上角的放大键）进大图；有底稿时是一条可拖动的竖线，左边原图、右边生成后，滑杆与方向键也能调；纯生成没有底稿，只放大单图并说明原因。
- 本地服务：校验图像、提交异步任务、轮询、下载并转为 PNG；API Key 存入 Windows 凭据管理器。
- 旧版脚本与新版命令提供快捷入口。快捷入口负责按选区分流到面板，仍需用户在面板确认并生成。

## 开发版使用方法

本仓库已生成三个开发加载包；插件在 Photoshop 菜单和面板中统一显示为 **AI 图像工坊**。需要 Windows、Node.js 20.9 或更新版本，以及北京地域百炼 API Key 和业务空间 ID。

1. 在 PowerShell 进入 [`dist/service`](dist/service)，运行 `node .\src\main.js`。保持窗口打开，记下它显示的“Local connection code”。预打包服务带有当前 Windows 环境的依赖；换机器或架构时先在此目录运行 `npm ci`。
2. 在**另一个 PowerShell 窗口**进入本仓库根目录，按 Photoshop 版本加载面板：
   - **2018（19.x）**：运行 `powershell -ExecutionPolicy Bypass -File .\release\install-dev-cep.ps1 -CsxsVersion 8`。
   - **2019–2020（20–21.x）**：同一命令改用 `-CsxsVersion 9`。
   - **2021（22.x）**：同一命令改用 `-CsxsVersion 10`；**2022–2023（23–24.x）**：改用 `-CsxsVersion 11`。这几版尚未实机验证。
   - **2024 及更新（25.x+）**：安装 UXP Developer Tool 并启用开发者模式，在工具中选择 **Add Plugin**，打开 [`dist/uxp/org.studio.aiimg.uxp/manifest.json`](dist/uxp/org.studio.aiimg.uxp/manifest.json)，点击 **Load**；在 Photoshop 的 **插件** 菜单打开 **AI 图像工坊**。[UXP 加载细节](hosts/uxp/README.md)。

   对使用 CEP 的版本，安装后重启 Photoshop，选择 **窗口 > 扩展 > AI 图像工坊**。[CEP 安装细节](hosts/cep/README.md)。

3. 点击面板右上角设置，输入本地连接码并点击“连接本地服务”；再填写百炼业务空间 ID、API Key，点击“保存百炼设置”。连接码只供本机插件使用；不要把 API Key 写入源码或 PSD。**用第三方 API 时**，「模型」是下拉框，只列实测跑通的模型，选中会连带把「尺寸模式」改成配对的那个（配错不报错，只会让回图比例跑偏）；清单里没有的模型选「自定义模型名…」手填，点「测试连通」先验一遍再保存。
4. 打开 RGB 8 位文档，框选区域，选“选区编辑”并点击“生成预览”。不写描述会自然补全；写描述会局部重绘。查看候选后点“应用候选”；想细看差别就点开大图，用中间的竖线在「原图 / 生成后」之间拖。扩图可选择四向比例，或先手工扩大画布并框选新增透明边缘；文生图则选“生成”。

旧版可选快捷脚本为 [`dist/cep/studio-selection.jsx`](dist/cep/studio-selection.jsx)，在 Photoshop **文件 > 脚本** 运行；新版命令名为“按选区打开 AI 图像工坊”。两者只把当前选区带入面板，不会自动提交付费请求。

三个包可通过 `release/build-cep.ps1`、`release/build-uxp.ps1`、`release/build-service.ps1` 重建，再运行 `release/verify-packages.ps1` 检查。服务自动测试：在 `service` 目录运行 `npm test`；面板逻辑测试：在仓库根目录运行 `node --test hosts/cep/test/*.test.js hosts/uxp/test/*.test.js`。

面板的控制器与样式只有一份源：[`hosts/shared/panel.js`](hosts/shared/panel.js)、[`hosts/shared/panel.css`](hosts/shared/panel.css)，两端目录里的同名文件是它的副本（CEP 用 `<script>` 加载、UXP 用 `require`，打包结构不同只能各放一份）。改完记得复制过去——`hosts/cep/test/panel-parity.test.js` 会校验两份副本与源文件逐字节一致，不一致就失败。

## 跨端约定

这三条以前只写在代码注释里，改代码前值得先看一眼：

- **`canvasBounds` 是几何真值**。扩图时面板把 Photoshop 的 `layer.bounds` 交给服务端，服务端只用它算「原照片在画布里的位置」。alpha 反推只是备胎：照片边缘有描边、投影或抗锯齿时它会算大，新增条带被挤成几个像素，最后合成一张几乎全透明的图——用户看到的是「扩图区合并后不见了」。
- **结果图必须是画布尺寸，且只有新增区有像素**。`apply` 依赖这个前提把结果贴成独立图层（原图层不动）；服务端返回别的尺寸时，面板会退化成「另开文档」并把原因写在状态栏。
- **扩图结果永远是独立图层，不再合并回原图层**。结果图的照片区是透明的，叠上去视觉等于「只补了边缘」，而原图层一个像素都不被改写——可对比、可单独删、不会把智能对象光栅化。想合并随时 Ctrl+E。图层名会标明 `AI 图像工坊 扩图` / `（整张画面）` / `（未对齐）`。
- **扩图底稿不能拿边缘像素循环复制**。`buildExpandInput()` 要把照片铺满目标画布，延伸区怎么铺直接决定模型画出什么。两种错法都踩过：整张镜像 → 人物、手被复制一遍；边缘窄条循环复制 → 窄条里本来就含着笔筒、书堆、桌沿的碎片，复制几次等于在延伸区盖了四五枚印章，模型照着画出「多出来的杯子」，用户看到的就是「内容接不上」。现在的做法是逐行/逐列沿趋势外推（边界色 + 饱和衰减的斜率），水平桌沿、竖直墙角继续走，物体形状不会被复制。
- **延伸比例本身就是一道保险，单边压在 15% 以内**。外推带里必然含有「被照片边界切断的物体」拉长后的影子，而延伸区有多宽，这条影子就有多长——24.6% 时白纸那一列色被铺成 243px 宽的横带，模型把它读成一个独立物体，于是在延伸区补出第二片纸和一条线缆，位置还和原物错开；换成 12.9%/11.1%（画布 2312×2844，同照片 `gemini-3.1-flash-image`）后一次通过：评分 0、`drift` 4.7、比例偏差 0.9%、接缝补偿实测差 8.1/12.6 全部补上。所以经验值是**单边 ≤15%**，>20% 明显更容易被编造。注意这个比例在面板上不是输入框，而是从画布透明边推导的（`layer.bounds` vs 画布尺寸），要控制它只能改 Photoshop 的画布大小。想一次扩更多，可以把结果当输入再扩一轮（未端到端验证）。
- **百炼的扩图靠「只送窗口」，双向扩图会退化成整张重绘**。百炼这条链路用的是指令式模型（`qwen-image-3.0-pro`），它没有「只画这一条带子」的能力，所以 `prepareExpandTask()` 改成把「新增条带 + 一截原照片」裁成窗口单独送进去：模型在原生分辨率下只看到接缝附近，`composeExpand()` 再把条带抠出来贴回画布（其余透明）——这也顺带解决了「整张压到 2048 见方再放大、扩展区天生糊一档」的问题。但**两条条带的并集一旦覆盖整幅画布，窗口方案就没有意义了**：`planExpandWindow()` 里「窗口几乎等于整张画布时交回整画布路径」那一关直接判空。右 + 下同时扩正是这种情况（右边条带占满全高、下边条带占满全宽），于是退回「整画布 + 指令式模型」，模型按「把画布向右扩」这句话把整幅重新构图，回来时照片区已被它自己顶掉。三个缺陷是叠加的：没有窗口、没有 composite、也没有 `extensionFidelity()` 那道「整张重绘」检测（那个只在 OpenAI 兼容链路里）。已修前两个——整画布路径现在也带 `composite`，模型画成什么样都只取新增条带，照片区恒为透明；降采样到 16 的倍数改成向下取整（`round` 会向上取整，2560×2880 会算成 1936×2176 = 4.21M，反而越过 2048² 上限）。**仍然没修的是内容**：双向时模型画的条带来自它自己的重构图，和原照片接不上，所以百炼上双向扩图仍然要一次一方向。
- **扩图提示词只有一份，在 `service/src/expand-prompt.js`**，优先级是「观感一致 → 不乱加东西 → 画出内容」，顺序不能反。它被三次翻车各改过一版：只写「材质要延续」→ 模型认为延伸区已经画好了，原样返回一片白雾；补上「被切断的物体要接上」→ 模型开始在延伸区**补完整套家具**，右边突然多出一个架子加一盆植物；现在是「先对齐景深和色温，再谈内容，没有明确该延续的结构时宁可是背景」。另一处关键：**用户的画面描述不能裸着放**，要包成「延伸区需要延续成：…」——裸放「右边接着白墙、木架和台灯」会被当成要新画进去的清单，模型就真的画一个新的木架出来。方向与幅度（向左/右扩多少像素、占原图百分之几）由 `bounds + canvas` 算出来写进提示词。
- **扩图尺寸：档位能用，但必须把比例一起发**。这条被两次实测各自修正了一半，两个前提都别漏。第一次是在 comfly 的 `gpt-image-2.6-flare` 上：`sizeMode: tier` 只发 `image_size=4K`、不发 `aspect_ratio`，而这一档的宽高比是**固定**的（一律回 3:2），画布 2738×2560（1.07）被当成 3018×2084（1.45）来画，模型不是在补右边而是在另一张比例上重新构图，`drift` 47~54。但第二次换到同一渠道的 Gemini（`gemini-3.1-flash-image`）后结论反过来了：**只要给了 `aspect_ratio`，它精确遵守**（请求 3:2 回 1264×848，偏 0.6%；请求 1:1 + 4K 回 4096×4096），而像素尺寸那边反而一律被压成 1024×1024——对 2600 画布是放大 2.5 倍，糊。所以现在的规则是：能推导出够接近的标准比例就走档位（4K 对 2600 画布是**缩小**），推导不出（偏差 > 4%）才退回像素尺寸。`aspectForCanvas()` 负责推导，`aspectBox()` 按推导结果做底稿——底稿比例必须等于 `aspect_ratio`，否则模型看到的留白占比和合成几何差一截，接缝会错开几十像素。
- **模型清单只放实测跑通的，尺寸模式跟着模型走**。清单里三个 ID 都真跑过同一张画布（3440×2560、右侧延伸 25.6%、真实照片）：`gemini-3.1-flash-image`（档位 4K，42s，drift 5.3，扩图首选）、`nano-banana-pro`（档位 4K，90s，drift 5.7，第 1 次就过；差别是紧贴照片边缘的那 15px 左右有一条拉伸拖影，1:1 看得出、缩略图看不出，所以定位成 flash 出问题时的备用而不是「更稳」）、`gpt-image-2.6-flare`（像素尺寸，扩图容易整张重画）。`gemini-3-pro-image` 这类「渠道里有、我们没验过」的名字不进清单——列出来等于承诺能用，而渠道缺这个模型时要等底稿传完才失败，用户只看到「等了一分钟然后报错」。`-2k`/`-4k` 后缀变体也不进：它们是固定分辨率，发 `image_size=1K` 照样回 4096×4096，跟「按画布推导档位」直接冲突；pro 系列更彻底，这个渠道上它不开 `/images/edits`（503），而扩图必须传源图，所以永远不可能走通。配错尺寸模式同样是静默失败，所以下拉一变就把模式改掉。清单外用「自定义模型名…」留出口，配合「测试连通」自证：按钮只敲 `GET /v1/models`，不生成图、不花钱；命中、未命中（附渠道里名字像图生图的候选）、渠道没有列表接口三种结果分开报，混成一句「连通成功」等于骗人去撞上传后的失败。
- **`gemini-3-pro-image` 系列不能用于扩图，不是「没验」而是「用不了」**。comfly 上 `gemini-3-pro-image` / `-2k` / `-4k` 三个 ID 全部返回 `503 不支持此 API 路径 [/v1/images/edits]`——扩图必须把源图连同遮罩送进去，走的就是这个路径，所以这族模型只能文生图。同一个模型的本家名字 `nano-banana-pro` 反而支持 `/images/edits`（1K 请求回 1200×896，说明认 `image_size`），但它单价更高、且未完成 4K 端到端验证，所以暂不进清单。`-2k` / `-4k` 后缀是**固定分辨率**：发 `image_size=1K` 仍回 4096×4096，`image_size` 被忽略——这类 ID 和我们「按画布推导档位」的做法冲突，不要用。
- **渠道按提示词文本缓存安全判定，同一个句子的 `451` 永远不会自己好**。实测同一条 comfly：一段固定的扩图提示词被 `451 The request was rejected by the content safety policy` 拒过之后，一字不差地重发四次全都被拒（响应越来越快，像命中缓存）；**末尾加一个句号就通过了**，加空格无效（渠道会归一化空白），换成 `padded` 形态（文本不同）也通过。也就是说这类拦截不是随机的、和画面内容也未必有关，而是绑定在文本上——固定的模板只要中一次，那条链路就永久失效，用户看到的是「昨天还能扩，今天这张图每次都失败」。两处防御：每次请求在提示词末尾带一个 `（请求编号 xxx）`，让文本永不与历史重复；`isPolicyBlock()` 把 451 和 Gemini 的 `finish_reason=17 / returned no image` 都识别为「这一种问法被拦」，不再当致命错误，而是换形态继续试；三种形态全被拦才报 `EXPAND_BLOCKED`，文案直接告诉用户改措辞（顺带堵住 `best` 为空时 `best.image` 的空指针）。
- **`aspect_ratio` 不要手填**。渠道设置里那个字段是「手动覆盖」，留空时每次按画布比例自动推导（1:1 / 4:3 / 3:2 / 16:9 / 21:9 …，按对数比误差取最近）。填死一个值，所有非该比例的画布都会被拉伸变形——而且没人会为每张画布改一次配置。
- **底稿尺寸必须等于请求尺寸**。以前 `preparedExpand` 只按 `apiSize`（1536 长边）做一次，之后不管向渠道要 2608×2560 还是 1024×1024，传上去的都是同一张 1536×1504——尺寸和图片对不上，中转站替你缩、或者按自己的比例重排，遮罩几何跟着一起错。模型拿到一张尺寸与要求不符的底稿，最省事的做法就是整张重画，这也是 `drift` 常年 36~57 的原因之一。现在按候选尺寸分别准备（`preparedFor` 缓存），`[upload]` 日志里也会打出图片真实尺寸。
- **渠道会把不认识的自定义尺寸换掉**，实测同一条 comfly：`1536x1520 → 2834x2220`（偏 23%）、`2608x2560 → 3132x2010`（43%）、`auto → 3094x2034`（40%），只有标准档 `1024x1024` 原样返回。三个候选全被判掉之后落到 1024，再放大 2.5 倍贴到 2600 宽画布，用户看到的就是「内容对不上」。所以比例被改写（`SIZE_ASPECT`）时会记进 `sizeRewrites`，并当场把「比例最接近画布的标准档」插到队首重试——分辨率低但几何对；之后再跑同一渠道直接走标准档，不再拿两次必败的请求去试。
- **回图比例要当场验，对不上就换尺寸而不是重试**。合成层会把模型回图直接 `resize` 到画布尺寸，比例差多少延伸区就被拉伸多少，38% 的偏差意味着接缝错位上千像素。这种图内容画得再好也不可能接上，判它「画得不对」是误诊，所以比例偏差 > 5% 直接抛 `sizeRejected` 换下一个候选。顺带一提，这也让「按 1536 生成再放大」成为常态，面板会明说「细节会比原图软一些，这是为了保住画布比例不变形」——这是有意的取舍，几何对 > 分辨率高。
- **扩图结果要过四道判定**。`extensionFidelity()` 把模型输出和上传的底稿逐像素比对，四种失败各有判据：扩展区几乎和底稿一致 → 原样返回；整块接近纯白 → 画成一片白；扩展区细节能量不到原照片同位置的一半 → 只有一片模糊色带；**照片区（mask 之外）平均漂移超过 10 灰阶 → 模型把整张画面重画了**。最后一种是「内容接不上」最常见的元凶：mask 明明只标了条带，它却整张重画，那它画的延伸区就是自己重新构图的结果，跟原图对不上是必然的。
- **判定的结果不是「过 / 不过」，而是一个分数**。四种毛病折算成 0~95 的 `severity`，100 专门留给「什么都没画」（原样返回 / 一片白）。一轮里会换三种**请求形态**各试一次——带遮罩的局部重绘、不带遮罩但保留留白底稿、只给原照片让它输出更大的构图；每种结果都留一份，最后挑分数最低的交出去。只有「三种形态都没画出任何东西」才报 `EXPAND_FLAT`；只要画了东西就照常出图，把毛病写进 `notice` 由面板显示。这条是被三连败逼出来的：模型每次都画了、每次都被判定不合格、每次都报错退出，用户花了三次钱，PS 里右边始终是空的棋盘格。
- **换形态比换措辞有效**。模型不听话时（尤其经中转站，mask 经常被直接丢掉），把同一句话改写三遍几乎总是拿到同一个错法。`bare` 形态完全不依赖遮罩语义：给原照片 + 「向该方向扩大画布」的文字说明，让它自己输出更宽的构图。它必然重画整幅，所以那种问法下「照片区漂移」不作数（`regenerated: true` 关掉 alien 判据），改用「把回图缩到原照片尺寸逐像素比」来识别「原样交回没扩图」，并给这形态一个底分 10——它永远排在「带遮罩、验证通过」的结果之后。
- **合成层要做景深对齐**。模型对「虚」几乎不敏感：给一块均匀色带，它倾向于补充细节，结果延伸区比原照片清楚一大截——内容就算接得上，眼睛也会立刻判断「这是拼的」。`composeExpand()` 会量出原图紧邻接缝那条带的细节能量，把过清楚的延伸区按级模糊压回同一水平（只压不锐，模糊不能凭空生出细节）。同一层还做接缝色延展与自适应色偏补偿：两侧差 60 灰阶以内按模型整体偏色处理（拉平），超过就当成内容本来不同（只补一点，避免把边缘压出暗带）。
- **色偏补偿要越过羽化带再采样**。补偿量算得对不对，全看「拿哪一条的颜色当生成区本色」。原来取的是离接缝 `feather`（24px）处——那里正踩在「从照片色过渡回生成色」的坡上，量到的自然是中间值。实测这一单（画布 2552×3142、照片 2048×2560、右侧 +24.6% 下方 +22.7%）：接缝紧邻处只差 4.5 灰阶（看着像已经接上了），但生成区深处比照片亮 20，补偿只给了 6，于是接缝旁留一条 25px 的软亮带——正是用户报的「边缘有点瑕疵」。改成取 `2*feather+16`（64px）后，实测差 11.7 / 14.7 灰阶被完整补上，竖直接缝台阶从 4.46 降到 **0.92**、`|台阶|`中位数 5.12 → 2.74，100% 缩放下已经看不出来。这条和上一条是同一个病例的两半：刀切边靠兜底，软亮带靠采样位置。
- **接缝柔化必须留一条兜底**。色延展的起点是「底图上接缝那一列的颜色」，取不到（底图解码失败、接缝整条落在透明区）时它会静悄悄地什么都不做——起点退化成生成色本身，成品上留一条刀切边，而日志全绿。实测遇到的就是这个：画布 2552×3142、照片 2048×2560，接缝正好在 x=2048，照片侧 105 灰阶、生成侧 112，过渡只有十几像素，再往里还有两三百像素的亮晕；100% 下就是一条竖线。现在 `softenSeam()` 返回 `applied`，没做成时由 `enforceSeamContinuity()` 兜底：逐行量接缝两侧 1~4px 的色差取中位数（用中位数不用均值，两侧内容本来就不同），超过 1.5 灰阶就按 5% 短边（上限 360px）的带宽线性拉平，单通道补偿上限 16 灰阶。兜底只在 `applied === false` 时启动，不会和正常路径打架——早期版本无条件跑，把色延展自己铺好的渐变又推了一刀，单元测试立刻炸。
- **`ECONNREFUSED` 在这条链路上不等于「地址写错」**。它和 `ECONNRESET`、TLS 握手失败一样，是「这一瞬间连不出去」——CDN 节点抖动、本机 NAT 表打满、公司网关掐新连接都长这样。实测同一条链路两次失败后，几分钟内连发 5 次全部返回 401（通的）。所以连接类错误单独走 `CONNECT_CODE`：退避 3s / 6s 再试两次（共三次尝试），报错文案也说「不是插件也不是模型」，避免用户去改一个本来就对的配置。
- **下载失败 ≠ 这张图没了**。结果图放在 `webstatic.aiproxy.vip` 这种图床上，它对这台机器的链路很爱掉线：日志里 18 次下载失败，多数重试一两次就过，有两次熬到第 5 次。所以 `fetchImage()` 给 8 次机会、退避 400ms 起翻倍封顶 6s（总窗口从 7.5 秒拉长到约 25 秒）。真全败时**不扔掉 `resultUrls`**：任务标成 `RESULT_DOWNLOAD` 失败但留着链接和下载函数，面板的「重试」先打 `POST /v1/jobs/:id/recover` 只重下这张图——几秒钟、不重新生成、不再计费。只有链接被回收（超过十分钟 TTL）时 `recover` 才返回 `NOT_RECOVERABLE`，面板这才退回完整重跑。
- **`X-STUDIO-Client` / `X-STUDIO-Token` 是鉴权契约**，面板与服务端必须同时改。Origin 白名单按 `plugin://` 前缀放行，所以扩展 ID 变化不会让面板连不上服务。
- **面板的视觉只有一处源，且必须按 Chromium 61 写**。`hosts/shared/panel.css` 是唯一源，CEP/UXP 两份副本逐字节相同（`panel-parity.test.js` 断言），DOM 结构则由 `preview/live.html` 跟真实面板保持同一套 id。视觉方向定为**暗房仪器**：石墨底 + 单一琥珀强调色。只有一种彩色的理由是它不能干扰画面判断——修图时盯着一块偏蓝的面板，眼睛会把照片看冷；琥珀是暗房安全灯的颜色，暖但不影响色彩中性判断。配套约定：所有数字（尺寸、秒数、倍率）走 `tabular-nums`，刷新时不左右跳；层次靠 1px 细线和灰阶差做，不靠卡片堆叠。**语法红线**：PS 2021 之前的 CEP 是 Chromium 61，`flex` 的 `gap`（84+）、`:has` / `:is`（88+）、`clamp()`（79+）、`conic-gradient`（69+）、`aspect-ratio`（88+）、`inset`（87+）全都不能用，写了会整条规则被丢弃——这类降级是静默的，界面上只是「没生效」，很难查。
- **面板的布局改过一轮，改的是信息层级而不是功能**。顶部原来叠了英文 eyebrow、大标题、文档信息框三层元信息，占了首屏三分之一；现在合成「标记 + 标题 + 文档副标」一块，`RGB 8 位`/`脚本版本` 这类只在排查时用的字段收进 `title`。渠道条从「带边框的整宽按钮」改成上下两道发丝线的信号行——它是状态不是输入，点和改都在同一处。扩图倍率从「一行四个数字 + 上下左右四个字」改成**画布示意图**：中间一块虚线的「原图」，四个数字贴在它的四条边上，方向即位置，不用在大脑里翻译一次。百炼下的「测试连通」暂时禁用（探针目前只解析 OpenAI 兼容的 `data[]`；百炼**其实能测**，走 `/api/v1/models` 的分页目录，见下一条）。这些改动都不碰 `panel.js` 的流程，只动 `index.html` 的结构、CSS 和少量文案。
- **「测试连通」只验三样东西，不能让它假装验了第四样**。探针发一个 `GET {地址}/models`，只回答：地址通不通、Key 有没有效、模型名在不在列表里。实测（`ai.comfly.org` / `gpt-image-2.6-flare`，2026-11-12）：真 Key → 200、909 个模型、命中；假 Key 与空 Key → 401；域名拼错 → `ENOTFOUND`；漏写 `/v1` → `normalizeBaseUrl` 自动补齐。**但这三类测不出来**：余额与配额、限流、以及「模型在线与否」——列表里存在 ≠ 此刻能出图（2048 档那个 503 就是活例），更不等于这张 Key 有出图权限（列表是全站目录，不是账号授权）。所以通过时文案后面必须挂一句「余额和出图权限还得真跑一次才知道」，别让人带着「连通正常」去点生成。
- **404 分两种，混在一起说会误导**。原来一律判成「渠道没有 `/models` 接口，能连上但模型名核不了」——可地址路径写错也是 404（`/v2`、`/api/v1`、多一层子路径），那种情况生成时照样 404，用户却刚被告知「能连上」。现在读响应正文：中转站（one-api / new-api 这一支）会明说 `Invalid URL (GET /v2/models), you may need [GET /v1/models]`，从中取出建议路径就判失败，并给出**能直接粘回去的完整地址**；正文里只有我们刚请求的那条路径、或干脆是 HTML 时，退回「核不了模型名」，不猜。宁可少说一句，也不要指一条和用户填的一模一样的路。
- **上游 503 分两类，重试预算必须分开**。用户报的现象是「有时候能用，有时候不能」：同一个 `1104x1536` 请求连发 4 次**全过**（每次约 20 秒），说明不存在「这个尺寸不支持」，而是中转站按「模型 + 尺寸」去上游池挑节点时容量时有时无。原来所有上游失败共用一个预算——1 次、固定等 1.5 秒，等于在同一个坏时刻又敲了一次门，所以自动重试几乎必然再败，用户只能自己手动点「重试」，还要把几 MB 底稿重传一遍。现在按措辞分两类：明确「没走到模型」的（`no available channel` / `pool` / `unavailable` / `capacity` / `busy` / 429）重试 3 次、退避 2 / 6 / 12 秒，合计约 20 秒，正好等于「用户等一会儿再手动试一次」的时间，只是不用他动手；其他 5xx 仍只补 1 次，因为那些可能是请求已经开始处理才报的错，多试会出两张图、扣两次费。失败文案也跟着分开：池子类必须明说「已经自动重试 3 次」，并补一句「不是这个尺寸不支持」——否则用户会把容量波动误诊成尺寸问题，去改一个本来正确的配置。
- **扩图比例的范围只能从「画布透明区」推，不能从「活动图层」推**。11 月 13 日用户报「识别不对」：2048×2844 的画布，活动层正好停在底部那条 285 高的透明带上。这个范围通过了 `saneBounds`（在画布内、够大、确实有新增区），于是被当成原照片——高 285 的分母把上方 2559px 算成 9.98 倍，直接被 1~2 的上限挡回，推导放弃，面板静静退回一个手填的默认值「右 1.5」，而画布上真实的扩张只有下方 1.11。这不是「偶尔算不准」，**活动层是画面里的哪一层完全是用户随手点的**，它随时可能是个小物件、一条透明带、或铺满整张画布的合并层。现在的规矩：`photoLikeBounds()` 先问「这个范围盖住了画面不透明区的多少」，盖不到一半就不是照片本体，直接作废；推导时两套范围都试（图层范围优先，失败退回 alpha 包围盒），任一套能给出 1~2 的合理组合就用。CEP 侧 `resolveInner()` 同样加了仲裁：`scalesDerived` 为真时把比例反解出的矩形当基准，图层范围和它差超过画布 2% 就不采用——否则「新增区」会被算成那条透明带，结果贴到画布外面，面板说「已合并」而画布上什么都看不见。
- **倍率框有两种身份，界面上必须分得开**。推导成功时它们是**读数**（灰、无边框、`readonly`，说明写「只显示、不能改」），推不出来时才是**输入**（可填，1.0~2.0）。不分开的代价是用户永远看到框里停着一个手填的数字，而实际用的是透明边算出来的另一个——他只能把结果理解成「识别不对」。配套两条：HTML 的 `right` 默认值从 `1.5` 改成 `1`（那个 1.5 是「为了让流程能跑」的兜底，不是任何人的意图，却成了误导的证据）；四个方向全是 1 时不再静默提交（那只会得到一张原样返回的图、还照样计费），而是说清楚「读不出透明边，先把画布往要扩的方向拉大」。


## 现阶段边界

当前机器没有 Photoshop，也没有百炼 API Key。CEP/UXP 在真实 Photoshop 的加载、羽化蒙版和回填位置未验证；[兼容性表](docs/compatibility-matrix.md)如实标记。大图的局部编辑会裁出最多 4096 像素的工作区域；整图重绘和扩图的输入画布上限是 8192 像素（超出模型输出能力的部分会自动降采样再还原）。四向比例扩图按「左上取整、误差归右/下」的方式吸收模型输出的 16 像素量化，尺寸对不上时另开文档。手工扩画布的结果也只有在输出尺寸与画布一致时才作为新图层应用。原生画布右键菜单没有接入；快捷入口位于脚本/插件命令菜单。

模型接口依据：[阿里云图像编辑 API](https://help.aliyun.com/zh/model-studio/wanx-image-edit-api-reference)、[阿里云 Wan2.7 图像 API](https://help.aliyun.com/zh/model-studio/wan-image-generation-and-editing-api-reference)。Photoshop 接口依据：[Adobe CEP](https://github.com/Adobe-CEP/CEP-Resources)、[Adobe UXP Imaging API](https://developer.adobe.com/photoshop/uxp/ps_reference/media/imaging/)。
